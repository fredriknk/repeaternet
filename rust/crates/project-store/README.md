# RepeaterNet project store

`repeaternet-project-store` opens the Python dashboard's v1 `projects.sqlite3` in place. It uses bundled SQLite, WAL, a 10-second busy timeout, and foreign keys on each connection. The two original tables, the workspace/update index, ID formats, and fractional Unix timestamps are preserved. Catalog schema versions newer than v1 are rejected.

## API

- Construct a `ProjectStore` with `new(database, data_root)`. Its methods use independent connections and can be called from worker threads. Use a blocking worker for HTTP handlers on an async runtime.
- Validate the 48-character lowercase hexadecimal cookie with `valid_workspace_key`. The server still owns cookie issuance and request authentication. Store queries and mutations are scoped to that key, including when a caller already has a project ID.
- Call `active(key)` when initializing a workspace. It reads the active selection, marks its queued, running, or preparing job interrupted, and falls back to the newest unarchived project or creates `Untitled plan`. Use `get` to refresh catalog data during a live session. `list_active` lists all unarchived projects, ordered by descending update time, and `list_archived` lists the archived projects in the same order.
- `create`, `activate`, `duplicate`, and `restore` select the resulting project. `rename`, `archive`, and `delete` operate on the supplied identity. `None` and `false` signal unavailable or ineligible rows. Name validation trims surrounding whitespace and uses the dashboard's 80-code-point limit. `NameInUse` covers collisions with either archived or unarchived rows in the same workspace.
- `autosave` keeps one previous revision if the plan value changes. `recover_previous` swaps the two SQLite revisions and clears the result summary. Create, autosave, recovery, duplicate, and restore also atomically replace the project-local `plan.json`. SQLite is authoritative, and `sync_plan_mirror` rebuilds that file if needed. Plan and summary fields use `serde_json::Value` to carry fields unknown to this crate.
- `project_path` re-reads ownership and the stored directory before resolving or creating it. Legacy rows with directory `.` can be opened, with permanent deletion blocked. Archive leaves files on disk. Duplicate copies only the current plan and the `dtm`, `dom`, `terrain-generations`, and `coverage-terrain-generations` trees, preserving terrain modification times. Delete removes both the catalog row and its inactive project directory. `storage_usage` counts regular files under the workspace, including archived and loose files.
- `set_run_state` and `save_result_summary` maintain the existing route-run metadata. The web server owns active-job guards, stale request and result detection, browser cookie lifetime, and route/coverage scheduling.

## Workspace integration

The crate is part of the Rust workspace. Run the tests and strict Clippy from the repository root.

```powershell
cargo test --locked --manifest-path rust/Cargo.toml -p repeaternet-project-store
cargo clippy --locked --manifest-path rust/Cargo.toml -p repeaternet-project-store --all-targets -- -D warnings
```

Construct the store before starting server workers or serving requests. Construction runs reconciliation automatically and returns an error if it cannot safely finish. Configure all Rust processes to use the same catalog and data root. The catalog directory must also be writable for the recovery journal.

The tests embed a checkpointed database generated by the original Python `ProjectStore`. It has two workspaces, an archived item, a saved summary and revision, and an inflight project. The plans cover Unicode, null, and an integer larger than 64 bits. Running the Rust tests requires no Python installation.

## Compatibility and limits

- Autosave ignores Python JSON whitespace and object key order when deciding whether to keep a revision. Standard JSON values are supported. Python's nonstandard `NaN` and infinity tokens cause a decode error.
- Paths are checked for workspace ownership, traversal, Windows aliases and device names, and junctions or symbolic links. Usage skips linked entries, while duplicate and delete reject linked trees. The configured data root is trusted. Use filesystem ACLs to prevent other local processes from replacing path components while the store is operating.
- Coverage manifests, terrain generation publication, fingerprints, and application-level import or browser-identity recovery belong to the callers. This crate reads the existing catalog, plans, and project paths and copies terrain trees without interpreting their contents.

## Crash recovery

The catalog's SQLite IMMEDIATE transaction serializes filesystem publication and reconciliation across Rust processes. A separate SQLite journal beside the canonical catalog path (`<catalog>.repeaternet-intent`) commits a single pending intent before creating or moving staged files. The catalog's v1 tables and schema version stay compatible with Python.

- Plan writes create an exclusive staging file alongside `plan.json`, then rename it into place. If rename completed, recovery compares the mirror with the committed plan and replaces it atomically when needed. If rename did not complete, recovery discards the staged file.
- Create and duplicate fill a staging directory, then rename it into place before committing the row. The staged directory carries an ownership marker. Recovery keeps a committed directory and clears its marker, or moves a marked, uncommitted publication back to staging and removes it. This also applies to the default project created during workspace initialization.
- Delete moves the directory to a unique sibling before committing the row removal. Recovery restores that directory if the row survived, or removes the staged tree if the deletion committed. If a live row's original path is occupied, recovery preserves both locations and reports an error.

Startup and subsequent catalog operations retry pending work. Stop concurrent Python or older Rust writers while using this protocol. Before switching back to Python, complete recovery with the Rust store. External filesystem edits, open handles, or unsafe paths can require operator intervention before recovery can proceed. Keep the journal beside its catalog until reconciliation succeeds. Recovery addresses abrupt process exit on a functioning filesystem. Power loss, filesystem corruption, and leftovers from older releases without intents are outside the protocol. Filesystem ACLs must prevent unrelated writers from replacing staging paths or journal files.
